Product Contract

Requirements

Summary

Design the UI/UX for the Paboxo money-market app by extending the existing coastal-glass system (src/styles.css) into every app surface, and by translating the interaction and safety patterns of the best DeFi lenders (Aave, Morpho, Spark, Fluid, Euler) plus number-heavy fintech craft (Mercury, Stripe, Linear) into that warm, calm surface. The default surface is a calm "Lite" front door with power-user density one tap away; risk is shown as buffer-to-liquidation with a named-zone scale and a live liquidation price; every risk-changing action previews its before→after effect; and every state — wallet, network, transaction, cross-chain, empty, loading, error — is designed against the mock adapter so real wiring is a data swap, not a redesign.

Problem Frame

The repository already has two of the three pieces: a finished visual system in src/styles.css and an implementation-ready integration plan that defines the data seam, hooks, and every functional action. What neither addresses is the app's interaction and visual design — how a market row looks, how health and liquidation risk are made legible without alarm, how a two-signature approve→act flow feels calm, how a multi-minute cross-chain supply communicates progress, how a newcomer is taught the three verbs of lending. Money markets are where UX carelessness is most expensive: a mis-shown health bar or a raw revert string can cost a user real money or their trust. This brief resolves those product-and-design decisions so planning builds screens against a settled UX, not an invented one.

Key Decisions

Direction: C · Tide (adaptive)

The app commits to the Tide direction — Harbor's calm surface as the default with a Simple↔Pro toggle that reveals density in place. Pro reveals reserved fields; it never re-lays-out. A · Harbor is the standalone fallback if v1 ships without the Pro state.

Calm "Lite posture" default, power on demand

The default surface is a savings-style front door; liquidate, delegation, allowance management and create-pool live behind an Advanced/Pro layer. Newcomers get calm; power users get density one tap away — the convergent finding across Morpho Lite, Spark, Pendle and Aave's "fintech test."

Buffer-to-liquidation + liquidation price over a bare health number

Health empties toward danger and carries a named-zone scale; the primary risk statement is "liquidates if X falls below $Y (−Z%)". The raw factor stays visible but subordinate. A full "100% = good" bar is banned.

Exact-amount approvals as a stated trust feature

Never unlimited/max-uint; the exact amount is surfaced before signing with reassurance copy. The extra signature is accepted and softened by the stepper — the security stance is made visible, not hidden.

One accent, semantic-only color, mono numerals

Lagoon is the only action accent; palm-green = positive, amber/coral = risk, always paired with label+shape. All financial numbers move to a tabular mono; Fraunces is reserved for titles and hero numbers — never inside data tables.

Every UX state designed against the mock adapter

Pending delays, wallet rejection, on-chain revert, indexer-down, and the cross-chain relay are all exercised in mock mode so the real contract/subgraph swap changes data, not screens.

Adapt Morpho's patterns, not its model

Paboxo is a classic isolated market with four hardcoded pools — not a curator/vault protocol. Curated-vault ideas (exposure clusters, APY provenance split, progressive disclosure) are borrowed selectively; the curator abstraction itself is out of scope.

Actors

  • A1. Newcomer — the primary UX persona; browses read-only, needs the three verbs taught.
  • A2. Lender — supplies liquidity, earns yield, withdraws.
  • A3. Borrower — supplies collateral, borrows pxUSDT, manages health, repays.
  • A4. Liquidator — advanced; repays unhealthy debt for a bonus.
  • A5. Delegator / Delegate — advanced; grants/exercises borrow or withdraw rights.
  • A6. Cross-chain supplier — supplies from Base via CCIP.
  • A7. Pool creator — advanced; creates and seeds a new market.

Product Requirements

Visual identity & design system

  • R1.App surfaces extend the existing coastal-glass system (tokens in src/styles.css) — sea-ink / lagoon / palm / sand, Fraunces + Manrope, island-shell glass, full light + dark. No new visual language is introduced.
  • R2.One saturated accent (lagoon) is reserved for primary actions and links; palm-green signals positive/yield/safe, amber/coral signals risk. Color is never the sole signal — each state pairs color with a label and a shape/icon.
  • R3.All financial numerals render in a tabular-figure mono face; Fraunces is used only for titles and hero numbers, never inside dense data tables.
  • R4.A standardized metric vocabulary (Supply APY, Net APY, Borrow APR, Utilization, Health, TVL) renders in the same slot, order, label, and color on every row, card, and panel.
  • R5.Number formatting is uniform: compact above 99,999 (K/M/B), 2-dp for USD and percentages, < 0.01 for dust, round-down for withdrawable/available amounts, per-token decimals read from token metadata (never hardcoded), and the user's own entered amounts and balances shown at full precision. A USD⟷token denomination toggle is sticky per user.

Information architecture & progressive disclosure

  • R6.Two planes: a public "all markets" plane viewable without a wallet, and a wallet-gated personal dashboard, with a single top-level nav switch between them.
  • R7.The default surface is calm (Simple), with power density one tap away (Advanced/Pro): retail sees supply / borrow / repay / withdraw, while liquidate, delegation, allowance management, and create-pool live behind Advanced with guided framing.
  • R8.Each market has a detail surface fusing live market data, the user's position, and its actions, deep-linkable by pool id.
  • R9.Once connected, a persistent portfolio strip shows total supplied, total borrowed, net APY, and aggregate health across the user's whole footprint.

Risk & health visualization

  • R10.Health is shown as a buffer that empties toward liquidation, plus a named-zone scale (Safe / Comfortable / Watch / At risk / Critical / Liquidatable) carrying color + label + shape; the raw health number stays visible but subordinate. A "full bar = good" representation is prohibited.
  • R11.The primary risk statement is the liquidation price / required price move ("Liquidates if X falls below $Y, −Z%"), shown alongside the health zone.
  • R12.Every risk-changing action (borrow, withdraw, repay) previews the projected before→after health and new liquidation price before confirm, recoloring live as the input changes.
  • R13.Danger is escalated through weight, opacity, motion, and a mandatory acknowledgment — not neon saturation; every warning is paired with an inline remedy (add collateral / repay).

Transaction & action flow

  • R14.All writes drive one shared transaction state machine (idle → approving → signing → pending → confirmed, with rejected and reverted/error terminal states); the primary button is its face, its label mutating through states, with a numbered stepper for multi-step approve→act.
  • R15.Wallet rejection is treated as a non-error (soft, no red, returns to idle); an on-chain revert decodes its reason to plain language, with the raw error kept behind a Details disclosure.
  • R16.Approvals are exact-amount only — never unlimited/max-uint — surfaced before signing as a stated trust feature; the approval step is skipped when an existing allowance already covers the amount.
  • R17.Optimistic UI applies only on confirmed (marked "syncing" and reconciled against the adapter), never on pending; success is a calm palm-green check, not gamified celebration.
  • R18.Pre-flight validation blocks invalid or unsafe actions before the wallet opens — insufficient balance, insufficient liquidity, unsafe projected health, and price feeds older than 1h.

Money input

  • R19.Every amount input pairs a token amount with a live USD equivalent (flip to switch denomination), a balance line, and quick-fill chips (25/50/75/Max); the amount field auto-focuses.
  • R20.MAX is context-aware: gas-reserved for the native token, risk-bounded to a safe-health floor for borrow/withdraw (not the theoretical max at HF 1.0), and capped by available liquidity.
  • R21.A mandatory "your new position" review precedes signing: amount, resulting balance, projected health + liquidation price, APY earned/paid, and the network fee in USD.

Wallet, network & states

  • R22.Read-only first: markets, APYs, and pool stats render without a wallet; only position-specific surfaces prompt connect (via Reown AppKit) through one canonical connect entry plus contextual inline CTAs.
  • R23.Wrong-network is handled proactively — a calm banner and one-click switch to HashKey 177 (with add-chain fallback) and no page refresh; every write verifies the target chain (177, or Base 8453 for cross-chain) before building the transaction.
  • R24.Every data surface specifies its loading (skeleton mirroring final layout), empty (a teaching new-user state with a next-action CTA), and error/unavailable states — including indexer-unreachable degradation that keeps on-chain balances and actions working.

Cross-chain, approvals & delegation

  • R25.Cross-chain supply from Base is a persistent, refresh-surviving multi-step tracker (Sent → Relaying (~est) → Arriving on HashKey), visually distinct from a local tx, with an expected duration / elapsed timer, a coastal in-transit motif, both-ledger explorer links, and a "taking longer than usual" recovery path.
  • R26.An approvals & delegation management surface lists active ERC20 allowances and delegations (spender, token, amount) with plain-language explanations and one-click revoke/reset (approve 0); delegation uses a deliberate flow distinct from the "Approve" chrome that restates the consequence ("you're letting 0x… borrow against YOUR collateral"), shows an exact cap, and requires an explicit confirmation.

Accessibility, onboarding & voice

  • R27.WCAG AA holds on the actual glass: text ≥ 4.5:1 tested against blurred backdrops in both themes, risk chips and critical numbers on opaque backing, a "reduce transparency" preference, and risk never signaled by color alone.
  • R28.Full keyboard operability, visible focus, aria-live announcements for health and transaction-status changes, and text alternatives for gauges/charts; tables collapse to cards below ~640px, touch targets are ≥ 44px, amount fields use inputmode="decimal", and prefers-reduced-motion is respected.
  • R29.First-run teaches the three verbs (supply to earn, borrow against it, health keeps you safe); read-only browsing is itself onboarding, and a no-wallet preview of the deposit flow is offered.
  • R30.A calm plain-language voice is the brand: every risk term carries a one-sentence tooltip, reassurance microcopy accompanies risky moments ("nothing happens until you confirm," "we only ever request the exact amount," "you can safely leave this page"), and errors name the cause and offer the fix.

Charts & data-viz

  • R31.Charts are quiet: a single palm-green/lagoon line with a soft area-gradient fade, one series, no gridline clutter, and frosted mono tooltips; allocation and utilization render as bar-in-cell (never pies), with optional row sparklines, following the one-accent rule for light/dark consistency.

Acceptance Examples

  • AE1 Stale price blocks. Given a feed's updatedAt is older than 1h, when the user opens a dependent action, then the FE blocks it and flags the feed as stale rather than sending a tx that would revert. Covers R18.
  • AE2 Borrow crossing into At-risk. Given a borrow amount that would push projected health below 1.25, when the user types it, then the buffer arc recolors live, the liquidation price updates, and an acknowledgment checkbox is required before the action enables. Covers R12, R13.
  • AE3 Wallet rejection is not an error. Given the user declines the signature in their wallet, when the flow returns, then it shows a soft "signature cancelled" and resets to idle — no red, no retry-shaming. Covers R15.
  • AE4 On-chain revert is explained. Given a mined tx fails, when the failure surfaces, then a plain-language reason is shown with the raw error behind a Details disclosure — never a raw hex selector. Covers R15.
  • AE5 Wrong network on a write. Given the wallet is on a chain other than the action's target, when the user initiates a write, then a switch prompt appears before the transaction is built. Covers R23.
  • AE6 Indexer unreachable. Given the indexer is down, when the user views a surface, then history/aggregates badge as unavailable while on-chain balances and actions keep working. Covers R24.
  • AE7 Cross-chain in-flight survives refresh. Given a Base supply has confirmed but not yet arrived, when the user reloads, then the tracker still shows "Relaying / arriving on HashKey," distinct from a local tx. Covers R25.
  • AE8 New-user empty dashboard teaches. Given a connected wallet with no position, when the dashboard renders, then it shows a teaching empty state with a Supply CTA, not a blank panel. Covers R24, R29.

Key Technical Decisions

KTD1 · A UI-kit layer the integration plan consumes

Presentational primitives live in src/components/ui/ as a standalone kit. Where the integration plan named src/components/{states,tx,wallet}, those are realized as (or re-exported from) the kit. This plan owns visual + interaction design; the integration plan owns data wiring. They meet at shared files.

KTD2 · Foundation sequences first

Tokens, the format library, and the metric-vocabulary primitives are a dependency the integration plan's UI units build on — they land before or alongside them, not after.

KTD3 · Tide density via a data-attribute + provider

A DensityProvider sets data-density="simple|pro" on a root element; CSS reveals reserved Pro fields in place (no re-layout). Persisted like the existing theme preference. Simple is the default.

KTD4 · Extend the existing theming, don't reinvent it

Build on the data-theme + light/dark class system and the @theme/island-* tokens already in src/styles.css and ThemeToggle. Add a tabular mono face, semantic risk tokens (--safe/--caution/--danger), and motion tokens — no parallel theming layer.

KTD5 · Primitives are data-agnostic

Kit components take props / render-props and never import adapters or hooks; the integration plan's hooks are consumed only at the composition layer, so the mock↔real swap never touches the kit.

KTD6 · Health is a pure, tested function

HF → zone mapping lives in one small module (src/lib/risk/health.ts), unit-tested once, reused by the meter, the zone chips, and the projected before→after preview — no re-derivation per component.

KTD7 · One formatting library

src/lib/format/ centralizes every number rule (R5); all surfaces import it. No ad-hoc toFixed in components — full precision kept internally, display formatted at the edge.

KTD8 · Motion is calm by default

Slow ease-out tokens (250–400ms), count-up on value change, skeleton shimmer over spinners; everything gated behind prefers-reduced-motion. No bouncy/springy motion — it fights the coastal calm.

High-Level Technical Design

The kit is a four-layer stack. Higher layers build on lower ones; the integration plan's data hooks feed in only at the composition layer, keeping the kit pure.

Build order: foundation → kit → shell → surfaces; advanced surfaces (U14–U16) and the cross-cutting quality pass (U17–U18) follow the core loop.

One tested utility implementing every formatting rule so no component formats numbers ad hoc.
Requirements
R5
Dependencies
U1
Files
src/lib/format/{number,amount,currency,index}.ts, src/lib/format/number.test.ts
Approach · Test scenarios · Verification

Approach. Pure functions over bigint/string inputs; per-token decimals passed in from metadata, never hardcoded; a denomination preference read from storage (sticky). Display-only rounding; full precision retained by callers.

  • Compact: 100,000 → 100K; 4,231,905 → 4.2M; 999 stays 999.
  • Precision: USD & % → 2 dp; a value < 1 → up to 7 dp; 0.004 → < 0.01, never 0.00.
  • Round-down: a withdrawable of 1.239 at 2 dp renders 1.23, never 1.24.
  • Decimals: same raw amount formats differently for pxUSDT (6) vs. an 18-dp token; decimals are an argument, not a constant.
  • Denomination: token↔USD flip converts using a passed price; the user's own entered amount is shown full-precision, not compacted.

Verification: all format tests green; a grep shows components import format rather than calling toFixed.
